이전 대화나 기획서는 필요하지 않습니다. 아직 앱 개발은 시작하지 않았으며, 기존 코드·DB가 있다고 가정하지 마세요.

먼저 README_START_HERE.md, AGENTS.md, docs/01~06을 읽고 실제 파일을 구현하세요.
설계 설명이나 계획만 제시하고 끝내지 마세요.
대상은 微博·小红书·豆瓣이며 처음부터 platform/object_type/native_id 공통 모델을 사용하세요.
豆瓣小组와 영화 리뷰는 별도 surface입니다.

기본 스택은 문서대로 사용하되 필요한 버전은 공식 문서로 호환성을 확인하고 고정하세요.
문서의 M0→M7 순서로 구현하세요.
첫 수직 흐름은 키 없이 사건 생성→세 플랫폼 fixture/import→품질→timeline→계보 근거→검토 보고서입니다.
그다음 반복 협조 분석, 안전한 수집 인프라, 실제 공급자 연동, 운영 검증까지 이어가세요.
단계별 완료 기준을 통과하면 다음 작업을 계속하세요. 매 단계마다 같은 실행 허가를 다시 요청할 필요는 없습니다.

사용자는 TikHub·JustOneAPI 유료 계정과 API 키를 보유합니다.
키는 서버 환경변수로만 사용하고 채팅·로그·fixture·frontend·git에 출력하지 마세요.
LIVE_PROVIDER_CALLS_ENABLED는 기본 false로 두세요.
실제 키와 명시된 호출/예산 상한이 없으면 해당 연동만 blocked로 기록하고 mock/import 및 독립 작업을 계속하세요.
새 유료 서비스 가입·결제·공개 배포는 하지 마세요.
실제 endpoint·응답·가격·권한은 최신 문서와 소량 fixture로 검증하고 추측하지 마세요.
豆瓣小组 API가 미확인이면 manual import를 유지하고 영화 API로 대체 완료하지 마세요.

다음 원칙을 반드시 구현하세요.
- 원본 receipt, 정규화 observation, analysis run, 사람 review를 분리.
- 외부 ID 문자열, 내부 UUID. 플랫폼 다른 동일 문구는 다른 객체.
- 게시/수정/관측 시간과 불확실 구간을 분리.
- 시간 선행·직접 참조·차용 후보·의미 유사·인과 효과·지시 관계를 구분.
- 같은 닉네임/사진으로 플랫폼 계정을 자동 병합하지 않음.
- 콘텐츠 전파/행동 협조/공개 운영 관계를 별도 그래프로 유지.
- 원문에 없는 인과 연결 추가, 추측→단정, 부정/반박을 근거 span과 함께 검토.

- LLM 없이도 핵심 기능 작동, LLM 제안은 근거 검증 전 초안.
- 모든 결과를 observation/revision/receipt까지 역추적.
- 재현 가능한 baseline, 검정 범위·효과·p/q·한계 표시.
- 분석 입력과 승인 보고서를 고정하고 새 자료는 새 버전.
